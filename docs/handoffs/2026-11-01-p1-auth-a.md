# P1-AUTH-A：登录持久化与密码自动填充

独立 worktree `D:/AIGC/p1-auth-a-20261101`，分支 `codex/p1-auth-a-login-persistence-20261101`，基于最新 main `ba0692f`。不修改 #44 分支；不合并、不部署。

## 诊断与根因范围

- **已确认的重复输入入口**：`/login` 原来从不检查已有登录，Middleware 也跳过登录页。因此从官网或书签再次进入 `/login`，即使浏览器仍有有效 Session，也总看到凭据表单。这是代码层面的可复现原因，不能据此认定生产 Cookie 已丢失。
- `@supabase/ssr@0.12.0` 默认通过 Cookie 保存 Session，默认 Cookie maxAge 约 400 天；Browser/Server Client 没有关闭 persistSession。没有发现“未开启持久化”配置错误，不新建认证系统。
- 原 Browser Client 没有现有调用者，页面打开后没有主动刷新会话的浏览器客户端；原先主要依赖服务端请求刷新。现在真实工作区挂载无视觉的 SessionSync，启动现有 SDK 的刷新，并处理标签页退出同步、返回页面时的服务端复核。
- 原表单已有 email/password 的 name/type、current-password/new-password 和 Server Action 提交语义。登录标识缺少 `autocomplete=username` 提示；已补齐。这提升密码管理器兼容性，不能保证浏览器必然弹出保存提示。
- 登录原本复用了注册的 8 字符最短限制，可能在 Auth 判断前阻止已有较短密码；现在仅注册保留最短限制，登录交给 Auth 验证。
- Middleware 原先忽略 SSR SDK `setAll` 的缓存响应头；刷新响应和其重定向现在保留 private/no-store、Pragma、Expires。
- **真实隔离 Auth 已复现**：`auth.sessions.not_after` 在过去、JWT 尚未到期时，`getUser(access_token)` 仍可返回用户。恢复逻辑先由 SDK 刷新，再用 Auth 验证同一个 Token，最后用参数化查询核对 Session id、user id、not_after 和 JWT 到期时间。查询/认证失败均拒绝恢复。没有修改服务端有效期、RLS 或权限。
- 未访问生产 Supabase、未使用 Owner 账号、未修改生产环境变量；无法从代码诊断确认生产浏览器清理 Cookie、隐私设置或服务端实际配置是否也是原因。

## 契约与交互

| 情况 | 行为 |
| --- | --- |
| 有效 Session 进入 `/login?next=…` | Middleware 先持久化刷新 Cookie，页面经服务端检查后跳到安全的受保护目标，默认 `/workspace` |
| 勾选「保持登录」 | 使用原 Supabase 持久 Cookie，可在浏览器重新打开后恢复，前提是 Cookie 保留且服务端 Session 有效 |
| 未勾选（默认） | 使用无 Max-Age/Expires 的浏览器会话 Cookie，刷新、同一浏览器会话及标签页共享有效；服务端和浏览器 SDK 刷新均保留这个属性 |
| 老用户无偏好 Cookie | 保留旧版默认持久化语义，避免使原有效会话突然失效；下一次登录采用新的显式选择 |
| 退出成功 | 保留 Supabase 原 global signOut 行为，删除本项目 SDK Cookie（包括分块和 PKCE），写入 signed-out 偏好，清理路由缓存，多标签页轮询检测后离开工作区 |
| 远程退出撤销失败 | 仍删除本浏览器 Cookie 并阻断恢复；显示其他设备可能仍登录的提示，不能声称远程已撤销 |
| 失效/撤销/过期 | 服务端拒绝自动恢复，受保护页面重定向到登录；缓存中的用户对象不作为授权依据 |
| 注册及邮件确认 | 保留现有策略，确认回调采用会话 Cookie；新注册的 PKCE 可在此前退出后完成 |

`aig-auth-persistence` 只保存 `session` / `persistent` / `signed-out`，不含密码或 Token，也不授予权限。持久化 Cookie 的 400 天是浏览器存储上限，绝不代表服务端凭据有效期。没有自建密码存储、没有自动提交密码、没有将 Token 放入 URL、日志或错误响应。

**浏览器语义限制**：启用“恢复上次会话”的浏览器可能恢复会话 Cookie；不承诺关闭窗口就等于退出。共享设备必须主动退出，也不应在浏览器密码管理器中保存该账号。密码保存、自动填充和删除由浏览器及用户控制。

SessionSync 仅挂载于 live AppShell 及 chat 布局，不进入公开 demo。它轮询非敏感偏好 Cookie（每 2 秒，无 Auth 网络轮询），退出时停止 SDK 刷新并执行完整页面跳转；焦点/页面恢复及 SDK SIGNED_OUT 时让服务端复核。页面隐藏时浏览器可能节流定时器，恢复焦点会再次检查。UI 仍使用既有设计，只新增一行选项和说明。

## #44 共同依赖

#44 使用 `createSupabaseBrowserClient().auth.getSession()` 为 Registry GET 请求按次获取 Bearer。浏览器工厂签名、SDK storage key、Token 格式和 Cookie 编码均保持兼容，同一 SDK singleton 动态读取最新偏好，避免刷新把 session-only 升为 persistent。`getSession()` 仍仅用于获取凭据，服务端负责授权。

本 PR 修改共享 `browser.ts`、`server.ts`、`middleware.ts`、`session.ts` 和 live AppShell 的无视觉会话挂载；没有编辑 Registry、Developer Console 或 Research Lab 业务代码。合并顺序任意，但 #44 合并/变基后仍应执行其真实读取的浏览器链路验收，不能覆盖 Auth 适配器。
